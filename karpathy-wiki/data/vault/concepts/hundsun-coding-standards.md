# 恒生电子编码规范总则

**恒生电子股份有限公司** 制定的《编码规范总则》，旨在统一公司各行业（编码语言、数据库等）的程序编码风格，提升软件的可读性、可维护性和可重用性。项目/技术支持组在软件开发和技术支持过程中必须严格遵守本编码规范。

> 程序风格是程序员编码素质的综合体现，程序员的编码水平＝编码规范＋编码效率。

---

## 1. 程序编写通用规范

### 1.1 基本要求

- 应用程序应按照相关编码语言的标准风格书写。
- 程序结构清晰、易读，单个函数的行数不易太多，应尽可能控制在 **100 行** 以内。
- 尽量使用标准库函数和公共函数。
- 使用全局变量要慎重，尽量使用局部变量。
- 多使用括号以避免二义性。
- 变量命名应符合项目组的命名约定。
- 不要修改编译器（开发工具）提供的函数。
- 不准使用不符合项目组规定的开发工具。

### 1.2 可读性要求

- 在所有命名中使用标准的英文单词或缩写，名称应含义清晰。
- **可读性第一，效率第二**。多加注释是提高可读性的重要办法。
- 保持注释与代码完全一致，边写程序边加注释。
- 每个源程序文件都有符合公司约定的文件头说明。
- 每个函数都有符合规定的函数头说明。
- 主要变量（结构、联合、类或对象）定义或引用时多加注释。
- 常量定义应加注相应说明。
- 处理过程的每个阶段都有相关注释说明。
- 利用缩进来显示程序的逻辑结构，缩进量一致并以 Tab 键为单位，Tab 占位长度统一为 **4 个字符**。
- 循环、分支层次尽量保持在三层以内，不宜超过五层。
- 技术支持阶段修改代码，必须增加注释，指明时间和修改原因、修改人。

### 1.3 结构化要求

- 禁止出现两条等价的支路。
- 用 `IF` 语句来强调只执行两组语句中的一组。
- 用 `CASE` 实现多路分支，`CASE` 内部尽量少用分支语句。
- 循环语句中避免多个出口。
- 函数最好是只有一个出口。
- 避免不必要的分支。

### 1.4 正确性与容错性要求

- 程序首先是正确，其次才是优美。
- 编写完一段程序后应先回头检查。
- 改正一个错误可能产生新的错误，修改前需考虑对其他程序的影响。
- 变量定义要注意类型（有无符号、范围是否足够等），所有变量在调用前必须确保初始化。
- 对所有的用户输入，必须进行合法性检查、安全性检查。
- 不要比较浮点数的相等（如 `10.0 * 0.1 == 1.0` 不可靠）。
- 不等式判别要注意由字长限制而引起的截短误差的影响。
- 程序与环境或状态发生关系时，必须主动处理意外事件（如文件锁定、打印机联机等）。
- 单元测试也是编码的一部分，提交联调测试的程序必须通过单元测试。

### 1.5 可重用性要求

- 可重复使用的、完成相对独立功能的算法或代码段，应抽象为 [[公共函数与代码复用|公共函数或类]]。
- 公共函数或类应减少外部联系，考虑独立性或封装性。
- 公共函数或类应建立引用模板。

### 1.6 独立性要求

- 出错信息或提示信息不准直接写入程序语句，应使用代码统一处理。
- 输入、输出程序要考虑不同型号的同类设备，尽量做到与设备相独立。
- **程序与数据相独立，程序与设备相独立**，是编码水平的重要标志。

## 2. 源文件版本及修订记录描述要求

各类源文件以文件为单位，在文件头部以注释形式描述以下内容：

### 源程序头部说明格式

| 字段 | 说明 |
|------|------|
| 源程序名称 | 本程序的外部文件名字（如 *.pas） |
| 软件著作权 | 恒生电子股份有限公司 版权所有 |
| 系统名称 | 本文件所在的系统或工程的名字 |
| 模块名称 | 本文件所在的功能模块名称 |
| 功能说明 | 简要说明本程序的功能 |
| 相关文档 | 相关详细设计文档号 |
| 作者 | — |
| 审核 | (可选的) |

### 源程序修改说明格式（以修改日期倒序排列）

```
修改记录:
  修改日期: YYYY-MM-DD
  修改人员: 姓名
  修改说明: 修改原因及内容
```

产品正式发布后，对源代码的任何修改必须留下修改记录。在源代码的实际修改处，应包含与修改记录中相同的日期、修改人员标识，并使用注释行表明实际修改范围。
