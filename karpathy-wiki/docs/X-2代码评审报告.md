## 一、逻辑错误

### F1 · `stream-run-manager.ts:106-119` — `onDone` 持久化失败被吞，仍广播虚假 `done`
`start()` 在 `chunk.done` 分支调用 `opts.onDone`（写会话 + 记忆）。若其抛错，仅 `catch → console.error`，`meta` 停留在 `{threadId:'', sessionId:'', messageIndex:-1}`；随后仍组装 `payload` 并 `broadcastDone` + 置 `entry.done=true`。
**影响**：客户端会收到 `done` 事件并 `finalizeAnswer`，但消息带上 `threadId:''` / `messageIndex:-1`：
- 下一轮提问因 `threadId` 为空 → 服务端新建线程，多轮上下文连续性被静默破坏；
- 该轮问答**未落盘**（session.json / memory.json 都没写成功），刷新后仅靠前端 IndexedDB 兜底；
- X-1 步骤追踪在空 `threadId` 下同样失效。
**严重程度**：中（仅在写入失败时触发，但触发后静默损坏线程连续性，且难以排查）。
**修正方向**：`onDone` 失败时不应以「成功」形态完成 run。建议：失败时置 `entry.failed=true`、`buffer.push({kind:'error'})`、`broadcastError`，交由 `runTask` 的 catch 统一收口，让客户端看到真实错误而非伪 `done`。

### F2 · `stream-run-manager.ts:94` — 同 `runId` 重复 `start` 无条件覆盖
`this.runs.set(runId, entry)` 直接覆盖既有 entry，未清理旧 entry 的 `evictTimer`，也未通知旧订阅者（旧 `subscribers` 直接丢弃，其 `subscribe` Promise 永远不 resolve，直到连接自身关闭）。
**严重程度**：低（`runId` 为 `randomUUID()`，碰撞概率极低，属防御性健壮性问题）。
**修正方向**：`start` 前若 `this.runs.has(runId)`，先对旧 entry `clearTimeout(evictTimer)` 并 `subscribers.forEach(s=>{s.end(); s._resolve?.('live')})` 再替换。

### F3 · `stream-run-manager.ts:111-119` + `query.ts` done 事件 — `DonePayload.runId` 误用 manager runId，破坏 X-1 步骤追踪
`payload.runId = runId`（即 `start` 入参的 **manager runId**），而非本轮 harness 的 `chunk.runId`。前端 `done` 处理器 `if (parsed.runId) writer.setRunId(parsed.runId)` 会把 X-1 步骤追踪的 `currentRunId` 设成 **manager runId**。
- 非恢复模式（原内联路径）`done` 发送的是 `runId: chunk.runId`（harness runId）→ 前端 `QueryTracePanel` 据此拉 `/api/query/runs/:runId` 正常；
- 恢复模式发送的是 manager runId → 该接口拿到的是 manager runId，**404 / 无步骤数据**，X-1 特性对恢复模式整段失效；且 `done.runId` 语义与关闭恢复时的行为**直接冲突**。
**严重程度**：中（恢复模式开启时，X-1 追踪静默失效；属于「恢复模式 vs 非恢复模式行为不一致」的逻辑/一致性 bug）。
**修正方向**：`payload.runId` 应取 `chunk.runId`（harness runId，作用域内可得）；manager runId 只经 `open` 事件下发，不应再进入 `done`。前端 `done`/`open` 处理器无需改动。

## 二、边界条件处理不当

### F4 · `frontend/src/utils/sse.ts:213-234` — `error` 事件未作为终止信号，浪费一次 resume 重试
当服务端回 `open` 后直接推 `error{RESUME_NOT_FOUND}`（200 + error 事件，非 HTTP 错误），`consumeQuerySSE` 正常返回（未抛错）。回到 `consumeQuerySSEResumable`：`didDone=false` 且 `managerRunId` 存在 → 进入 resume 分支，用同一 `runId` 再请求一次，再次命中 `RESUME_NOT_FOUND`，直到 `resumeCount>=maxResume(1)` 才 `finalize` 退出。
**影响**：消耗了唯一一次 resume 额度在无意义的「找不到 run」上；极端情况下（首连已收到部分 answer 又推 error）`resetForResume` 已清空 `streamingAnswer`，二次 error 因 `streamingAnswer` 为空不再推消息，状态可控但体验冗余。
**严重程度**：低（功能正确，仅浪费一次重试、延迟最终 finalize）。
**修正方向**：在 `SSEWriter` 上暴露 `didError` 标志（类似 `didDone`），`consumeQuerySSEResumable` 在 `consumeQuerySSE` 返回后优先判 `didError` → 直接 finalize 不 resume。

### F5 · `query.ts:430-459` — `handleResumeRun` 无线程归属校验
resume 仅校验 `streamRunManager.has(runId)` 与 UUID 格式，**不校验当前用户是否拥有该 run / 其 threadId**。runId 为不可猜 UUID，实际越权风险低，但与本项目严格的 `guards.requireAuth` + thread owner 校验基调不一致（信息暴露：若 runId 泄露，可重放他人答案内容 + threadId）。
**严重程度**：低（信息暴露，无写入；UUID 不可猜）。
**修正方向**：`start` 时把 `ownerId` 绑进 `RunEntry`，`handleResumeRun` 比对 `request.currentUser?.userId`，不符则 `RESUME_FORBIDDEN`。

### F6 · `frontend/src/utils/sse.ts:218` — 网络骤断（抛错型）不触发 resume（见 F10）
`consumeQuerySSEResumable` 仅在 `consumeQuerySSE` **正常返回**（流 FIN）时才判 `didDone` 进入 resume；若 `reader.read()` 抛错（RST / 连接重置 / 超时异常），异常直接穿透 `await consumeQuerySSE(...)` 未被内层 `try` 捕获 → 冒泡到调用方 catch → 视为真实错误，不重连。
**影响**：与「网络中断可恢复」目标部分背离——优雅 FIN 能重连，但最常见的**骤断**反而直接报错。
**严重程度**：中（恢复能力覆盖不全，是 X-2 核心目标的缺口）。
**修正方向**：将 `await consumeQuerySSE(...)` 用 `try/catch` 包裹，非 `AbortError` 且 `managerRunId` 存在且 `resumeCount<max` 时走 resume 而非抛错；`AbortError`（用户主动停止）保持原样退出。

## 三、空值或异常未处理

### F7 · `stream-run-manager.ts:104` — `chunk.webRefs ?? [] as WebRef[]` 强制类型断言
`(chunk.webRefs ?? []) as WebRef[]` 用 `as` 绕过类型校验。若 `AnswerChunk.webRefs` 运行时结构与 `WebRef{title,url,snippet}` 不符（如字段命名差异），前端 `refs` 合并会得到错误 webRefs。
**说明**：该风险与内联路径（直接 `chunk.webRefs ?? []`）同源，属既有隐患在恢复模式的复刻，非 X-2 新引入。
**严重程度**：低。
**修正方向**：在 `dispatchStreamChunk` / `onDone` 处做字段级归一化（映射为 `WebRef`），而非整对象 `as` 断言。

### F8 · `stream-run-manager.ts` `subscribe` 回放顺序 — 无实质问题（确认项）
回放循环（165-169）与 `entry.subscribers.add(sink)`（174）均为同步、无 `await` 穿插，依赖 JS 单线程模型，**不存在「回放中漏掉刚到达的 live 块」的竞态**。此为正确实现，列出仅为确认。
**严重程度**：无。

## 四、潜在死循环或性能隐患

### F9 · `stream-run-manager.ts:165-169` + 全量 buffer — 同步回放阻塞事件循环
`entry.buffer` 在 run 全生命周期 + TTL（默认 5min）内保留**全部** chunk；`subscribe` 回放是一次性同步 `for` 循环，每个 chunk 调 `sink.onChunk` → `dispatchStreamChunk` → `send()` 写 socket。对于历史出现的超长回答（143s/282s），buffer 可能含数千个 chunk 对象，回放会在一拍内同步写回整段答案。
**严重程度**：低–中（典型回答无感；超长回答下出现短暂事件循环卡顿 + 输出突刺）。
**修正方向**：回放改为分片 `await` 微任务让出（如每 N 个 chunk `await Promise.resolve()` 或 `setImmediate`），或对 buffer 设置上限（超限时回放改为「重新跑 producer」而非全内存回放）。

### F10 · `stream-run-manager.ts:96-130` / `253-259` — producer 卡死无 watchdog，run 永久泄漏
`start` 仅当 `iterate` 正常 `return`（done）或抛错才 `finishRun`；若 harness producer **既不发 done 也不抛错**（历史 282s 虽最终结束，但存在卡死可能），`entry.finishedAt` 永不为设、`evictTimer` 永不被建 → run 在 `this.runs` 中常驻（buffer + `subscribers` 持续占内存），直到进程重启才回收。
**严重程度**：低–中（依赖 harness 可靠性；一旦卡死即内存泄漏 + 连接悬挂）。
**修正方向**：`start` 内加整体超时 watch（如 `maxRunMs`），超时强制 `entry.failed=true` + `broadcastError` + `finishRun`，避免永久悬挂。

## 五、与原有代码行为不一致

### F11 · 一致性核对结论（**通过**，无回归）
逐事件比对 `dispatchStreamChunk`（恢复模式）与原内联路径（`dispatchProgressEvents` + 主循环）：thinking / progress / image / ppt / followups / multimodal / answer / refs / done / open 事件**全覆盖**，`governor`、`runId`、`webRefs` 字段均透传。唯一差异：恢复模式的非 done chunk 携带 refs 时，`dispatchStreamChunk` 的 `else if` 分支会**一并带 `webRefs` 内联下发**，而内联路径仅于 `done` 时发 webRefs —— 属无害超集，不影响渲染（前端 `bufSetRefs` 整体覆盖 `currentRefs`）。
**结论**：事件级行为与原实现一致，恢复模式未引入事件缺失。

### F12 · `done.runId` 语义不一致（即 F3）
非恢复模式 `done.runId` = harness runId；恢复模式 `done.runId` = manager runId。同一前端字段在两种模式下含义不同，属明确的不一致。详见 F3。

### F13 · `query.ts:127-129` 开关切换的边缘不一致
`resume` 短路依赖 `enableResumableStream` 同请求期为真；若服务端在两次请求间热切换该开关（同一客户端仍持有旧 `managerRunId`），客户端发 `resume:` 会因开关已关而落到 BYOK / question 校验 → 400。
**严重程度**：低（仅 config 热变更才触发，且客户端无 `open` 时本就不会发 resume）。
**修正方向**：无需特殊处理；若未来支持配置热更新，可在 resume 短路处对「开关关闭但收到合法 resume」返回 `RESUME_DISABLED` 友好提示而非 400。

## 六、可读性与可维护性问题

### F14 · `stream-run-manager.ts` `RunSink._resolve` 泄漏进公共接口
`RunSink` 接口（49 行）含 `_resolve?: (v:'live')=>void`，由 `subscribe`（176）、`unsubscribe`（185-188）、`broadcastDone`（223-226）、`broadcastError`（245-248）直接读写。内部 resolver 暴露在公共订阅者契约上，调用方（`query.ts`）构造 `RunSink` 时虽以可选省略，但耦合不清晰。
**严重程度**：低。
**修正方向**：用模块内 `Map<RunSink, resolver>` 保存 resolver，把 `_resolve` 移出 `RunSink` 接口。

### F15 · `Query.vue:642/650`、`FloatingChat.vue:166/173`、`MobileQuery.vue:484/492` — 非 null 断言依赖控制流假设
`initialFetch` / `resumeFetch` 闭包内用 `abortController!.signal` / `activeAbort!.signal`。类型上 `abortController` 为 `| null`，TS 在箭头内丢失收窄，故加 `!`。编译通过（TSC_EXIT=0），但依赖「闭包只在控制器存活时同步触发」的隐式假设，属 smell。
**严重程度**：低。
**修正方向**：定义闭包前先 `const sig = abortController.signal;` 提为常量，闭包内用 `sig`，去掉 `!`。

### F16 · 命名易混
- `StartOptions.onDone` 与 `RunSink.onDone` 同名不同义（前者持久化回调，后者推给 SSE）；
- `DonePayload`（广播载荷）与 `DoneContext`（onDone 入参）命名接近易误读。
**严重程度**：低。
**修正方向**：重命名为 `PersistCallback` / `OnDoneSink` 与 `DonePayload` / `DoneArgs` 之类区分更清晰的名字。

### F17 · `query.ts:388-399` / `443-454` — `RunSink` 构造重复
`handleResumableStart` 与 `handleResumeRun` 各自构造几乎相同的 `RunSink`（约 12 行）+ 相同的 `reply.raw.on('close', ...)` 监听，违反 DRY。
**严重程度**：低。
**修正方向**：抽 `buildRunSink(reply, request, runId)` 工厂，两处共用。

### F18 · `consumeQuerySSEResumable` `maxResume=1` 硬编码（见 F4）
默认重试次数写死，且被 `RESUME_NOT_FOUND` 这类「注定失败」的情形消耗。
**严重程度**：低。
**修正方向**：作为可配置参数（或至少注释说明为何为 1），并与 F4 的 `didError` 短路配合避免浪费。

### F19 · 部署态提示（非 bug）
`api/config.json` 当前 `enableResumableStream: true`（本会话验证用）；`defaultConfig` 默认 `false`、`index.ts` 经 `?? false` 兜底，关闭时完全不走恢复分支（零破坏纪律成立）。上线前需确认是否保持开启——若保持开启，F1/F3/F6/F10 的修复优先级应上调。
**严重程度**：信息。
