## 2. 发布前检查清单

### 2.1 代码与构建

- [ ] 工作区干净：`git status` 无本期待发布文件的未提交改动
- [ ] 后端全量：`cd api && npx vitest run` → exit 0（基线 61 文件 / 855 用例）
- [ ] 前端全量：`cd frontend && npx vitest run` → exit 0（基线 67 文件 / 616 用例）
- [ ] 双端类型：`npx vue-tsc --noEmit`、`npx tsc --noEmit` → exit 0；后端另跑 `npm run typecheck:test`（T02903 起覆盖 api/test+scripts）→ exit 0
- [ ] 生产构建：`npm run build` → exit 0（主题 token 校验内置于构建）

> 注意：全量套件里有 3 个**耗时由真实磁盘/CPU 主导**的文件（`src/workflows/batch-fix-job.test.ts`、
> `test/pptx-renderer-real.test.ts`、`test/auth-rate-limit-route.test.ts`），它们已按实测值设了显式超时。
> **不要与 `npm run build` 并发跑**，否则计时敏感用例会假失败——遇到红色先隔离复跑再判回归。

### 2.2 运行时复核（三期踩过的坑，必须做）

- [ ] **重启 api 实例**（旧进程不会热载 `api/src/vault/page-scope.ts` 等模块级改动）
- [ ] 重启后核对「仪表盘 页面总数」与「页面质量清洗 页面总数」**显示同一个数**
      —— 真实库基线随投递增长，**不锁死具体数值，以「三处同数」为准**
      （2026-10-22 T02729 实测基线 **245**：entities 43 / concepts 166 / comparisons 9 / queries 9 / qa 18 / solutions 0；
      entities 目录另有 `test-doc-2.md`、`proxy-test-2.md` 两个联调遗留，按口径不计入页面）
- [ ] 图谱页「共 N 个节点」与上述两处一致（三处同源，见 `api/test/page-scope-consistency.test.ts`）
- [ ] 登录页**不再出现明文默认账户**；出厂 admin 若仍是默认口令，页顶出现改密告警
- [ ] 随机抽 3 个菜单确认：菜单名 = 页标题 = 帮助文档条目名（术语表 §3 口径）
- [ ] 打包形态复核运行状态目录：起一次 exe 并跑完任意一次 compile 后，确认
      `%LOCALAPPDATA%\KarpathyWiki\data\.harness\state` 已生成且清理页「运行状态」**首项（canonical）计数 = 磁盘实数**；
      exe 旁与启动目录**不应**新增 `.harness/state`；把一份旧状态文件放进 exe 旁遗留目录，`/api/compile/runs` 仍应列出它
      （2026-10-25 T02810 实测：canonical 2 = 磁盘 2，两处遗留目录 0，旧目录探针可见并可清理）

> 为什么单列一项：10.1 真机回归时出现过「页面质量清洗 216 / 仪表盘 245」。取证结论是

> 也就是说这一项查的是「发布产物是否真的带上了代码」，源码看不出来。派生单 T02729
> 已于 2026-10-22 收口：dev（tsx）与发布包（`release/api-dist` + `release/spa/public`）两种形态各起一个隔离实例，
> 仪表盘 / 页面质量清洗 / 图谱「共 N 个节点」三处 UI 实测均为 245（`/api/stats`、`/api/graph`、
> `/api/data-clean/pages` 四条链路同数）。本清单原基线 243 系 10-20 快照，此后 entities/comparisons 各新增 1 页，基线随库更新。

### 2.3 发布动作

- [ ] 版本号：`scripts/bump-version.ps1` 由构建流程写回 `package.json`（规则 `0.1.{YYYYMMDD}{seq}`，主/次版本手工维护）
- [ ] 发布说明落盘：把 `docs/wiki三期/06-发布说明.md` 复制为仓库根 `release-notes-<新版本>.md`，
      或正式发布时用 `-ReleaseNotesFile <path>` 显式指定（脚本会落地为约定名）
      （`publish-wiki.ps1` 的 `-PublishRelease` 按 `release-notes-<package.json 版本>.md` 取文件；
      **约定文件缺失或只剩 `.auto.md` 时脚本直接阻断发布**，不再用 git log 自动兜底——
      旧版「自动生成 `.auto.md` 仅警告后继续」的口径已于 T02743 废除；`-DryRun` 对同输入只告警不阻断，可作预检）
- [ ] 安装包（可选，走 GitHub Release 时需要）：`scripts\build-exe.bat` → 产物落 `release/installer/KarpathyWiki-Setup-v<版本>.exe`
      （脚本会优先挑**与版本号匹配**的安装包，防止 bump 后忘构建、把旧包装进新 tag）
- [ ] 先干跑：`scripts\一键发布.bat` 等价 `powershell -File scripts\publish-wiki.ps1 -DryRun`，核对将执行的 6 步命令与部署目标
- [ ] 正式发布：`scripts\一键发布.bat`（安装依赖 → 构建 SPA → 部署 `release/spa/public` → 重启生产服务 → 健康检查）
- [ ] 需要对外发 Release 时加 `-PublishRelease`（token 走 `.env` 的 `GH_TOKEN` 或 git 凭据库，脚本不打印不落盘）
- [ ] 发布后冒烟：`http://localhost:<apiPort>/health` 返回 ok、`http://localhost:<apiPort>/wiki/` 能打开、
      再跑一遍 §2.2 的运行时复核（发布过程本身就是重启服务，正好在此确认）
