## 4. 技术调研：路由改造方案（N4 / T02394 前置结论）

**现状证据**：
- `frontend/src/App.vue:53` `menuItems` 15 项；`const currentView = ref<ViewName>('dashboard')`；`go()` 权限守卫（`App.vue:108-111` 附近，校验失败仅 `console.warn`）。
- 全项目 **无 vue-router**（6 处注释显式声明不引入：App.vue / useIsMobile.ts / Query.vue / MobileBrowse.vue / MobileShell.vue / RefsList.vue）。
- 跨视图跳转已有 CustomEvent + sessionStorage 机制（Query.vue）；移动端 MobileShell 独立 tab 切换。

**方案对比**：

| 方案 | 成本 | 收益 | 风险 |
|---|---|---|---|
| A. hash 同步 currentView（`#/query`） | 中（1 个 composable + go/App 接线） | 刷新保持/回退/深链全解决 | 低：不动渲染架构，与「不引入 vue-router」约定一致 |
| B. 引入 vue-router | 高（15 视图改路由表 + 守卫迁移 + 移动端分支） | 同上 + 嵌套路由未来能力 | 中：违背项目既有约定，回归面大 |
| C. 不改 | 0 | 无 | N4 保持 P0 |

**结论：选 A（hash 同步）**。落点：`composables/useHashView.ts`（hashchange 监听 + `go()` 内同步 hash + 非法 hash 回落 dashboard + 移动端 hash 不联动或只读映射），T02394 实施。

## 3. REQ-038 的取证过程：为什么 216 与 245 又同时出现了

真机对照时，页面质量清洗显示「页面总数 216」，仪表盘显示「总页面数 245」——正是 8.1（T02472）声称修掉的矛盾。逐层定位：

1. `GET /api/data-clean/pages` 返回 216 条，目录分布为 concepts 166 + entities 42 + comparisons 8，**完全没有 queries 与 qa**；
2. `GET /api/stats` 返回 totalPages 245、dirCounts 只有 4 个目录（entities 计 44，含 `test-doc-2.md`、`proxy-test-2.md` 两个联调遗留）；
3. 216 恰好等于「concepts + entities + comparisons 三目录白名单」的**旧口径**，而 245 = 243（当前口径）+ 2 个测试遗留；
4. 检查进程：`:3000` 上的 api 进程启动于 2026-10-19 05:15，而 `api/src/vault/page-scope.ts` 写入于同日 10:53 —— 该实例跑的是 T02472 之前的代码，且未热载。

用当前源码在 fixture vault 上重跑四条链路（`api/test/page-scope-consistency.test.ts`）：`scanVault`、`/api/stats.totalPages`、`dirCounts` 合计、`buildLinkGraph` 节点集两两相等，且都排除 `test-*.md`/`proxy-test*.md`/`drafts`/`raw`/根索引。

又把同一套断言在**真实 vault** 上跑了一遍（一次性取证，跑完即删，不入家用例）：

```
[REAL-VAULT] {"vault":"…/karpathy-wiki/data/vault","scanVault":243,"statsTotal":243,
              "dirCountsSum":243,"graphNodes":243,
              "dirCounts":{"entities":42,"concepts":166,"comparisons":8,"queries":9,"qa":18,"solutions":0}}
```

四条链路在真实数据上同为 **243**，且 `entities` 是 42（两个 `test-*.md`/`proxy-test*.md` 联调遗留已被 `isPageFile` 排除）——旧实例报的 245 正是「没排除遗留 + 旧目录白名单」的组合。

结论：**代码层口径一致，真机差异来自未重启的旧实例**。这条已经转成 10.2 的发布检查项（见派生单），不再靠「我记得改过了」。

同一轮也暴露了守护本身的缺口：`p0-regression.test.ts` 只能证明「前端常量与后端 PAGE_DIRS 字面相同」，证明不了三条统计链路真按这份口径取数——所以补了上面那个运行时测试，把「三处同一个数」钉住。

# 六、三期发布说明（原 06，面向用户）

> 面向对象：日常使用者（知识组）与管理员（运维/系统组）
> 范围：wiki三期 M2~M9 的全部用户可见变更
> 详细验收证据见 `04-P0需求回归测试报告.md`，发布动作见 `05-验收报告与发布检查清单.md`

## 一句话总结

这一期没有加新功能，而是把已有的 15 个功能菜单**改成找得到、看得懂、敢点**：导航重新分组、术语全站统一、
关键数字三处对齐、危险操作有确认、长任务能中断也能续跑。

## 你需要先知道的 3 个变化

1. **左侧菜单分成 4 组**：知识（仪表盘 / 知识浏览 / 知识问答 / 知识图谱）→ 生产（投递资料 / 编译进度）→
   运维（体检中心 / 缓存与日志清理 / 页面质量清洗）→ 系统（配置中心 / 内网穿透 / 用户管理 / 技能管理 / 帮助文档 / 关于）。
   以前滚到底会点不动的菜单项，现在全部可达。
2. **两个名字变了**（点的地方没变，只是名称更能说清它干什么）：
   - 「系统清理」→ **缓存与日志清理**：只删运行产生的缓存与日志，不动知识库内容。
   - 「数据清洗」→ **页面质量清洗**：处理的是知识库页面的质量问题。
3. **页面总数只有一个口径**：仪表盘、页面质量清洗、知识图谱三处显示的数字现在来自同一份计算，
   不会再各说各话。如果你刷新后看到两处不一致，说明后端还是改动之前启动的旧进程——**重启服务即可**。

## 按菜单的变更明细

### 仪表盘

- 目录分布条按比例正确绘制（原来所有条一样长，看不出差异）。
- 数据加载时显示骨架屏，不再「用空白冒充加载中」。
- 快捷入口不再是假可点，点了真的跳转。

### 投递资料 / 编译进度

- 主按钮「开始编译」统一配文字说明，悬停即写清这次会编译哪些内容、多少个页面（例如「将勾选的 12/30 个页面与附件编译为知识库页面」），提交前就知道范围。
- 编译各阶段显示中文（存档原始资料 → 读取结构规范 → 抽取要点 → 生成页面 → 更新索引 → 记录日志 → 收尾），不再出现 `read_schema`、`done` 这类内部词。
- 编译历史与仪表盘的运行历史走同一份数据，两边数目对得上。
- 取消入口统一，取消后状态明确。

### 知识浏览 / 知识问答 / 知识图谱

- 问答输入条的图标全部带文字标签，暂未实现的能力不再摆在那儿诱人去点。
- 「发送」「停止」恢复文字（这是最高频动作，纯图标让人反复猜）。
- 长回答支持排队输入；「断点续答」改称「重新生成」并把代价说清楚——它确实是从头重答，触发时会提示「将重新消耗一次问答额度」。
- 输入框上方常驻显示当前模型名与来源，回答出自哪个模型一目了然。
- 图谱默认按连接度取 Top-N 节点并显示标签（原来几千个点糊成一团毛球），支持搜索定位、选中后给出显式操作按钮。

### 体检中心

- 问题列表支持搜索、多选、分页，同类问题聚合计数。
- 批量修复改成后台作业：可暂停、可继续、可取消，断线重连后进度还在，并给出预计剩余时间。
- 中断也不再丢进度（快照与耗时统计现在原子落盘）。

### 配置中心

- 11 个标签页按「个人偏好 / AI 服务 / 系统」三组左侧导航排列，不用横向滚动找。
- 每个字段标明生效方式（即时生效 / 热加载 / 需重启），页顶汇总「哪些改动还没生效」并给出一键重启指引。

### 内网穿透 / 缓存与日志清理 / 页面质量清洗

- 启动失败时把后端原因直接显示在页面上（端口占用、token 未配置等），并前置自检三项条件，不用翻日志。
- 「仅预览」升级为页级单一开关：默认开启，关掉之后本页所有清理按钮才真的删除，顶部同时出现红色横幅 + 二次确认。
- 页面质量清洗不再给一个「平均分」让人猜，改成 5 类可操作问题（缺元信息、标题重复、无出链、字数过短、读取失败），每类直接配批量动作；表格支持搜索、按目录筛选、点列头排序、分页且翻页保留勾选。

### 用户管理 / 技能管理

- 列表统一为同一套表格组件，创建/编辑改用统一弹窗。
- 删除自己、禁用最后一个管理员这类危险操作被真正拦住；出厂账号若仍是默认口令，页面顶部会出现改密告警。
- 登录页不再明文展示默认账户。

### 全站

- 建立《术语表》作为单一可信源：菜单名 = 页标题 = 帮助文档条目名 = 提示语里的路径名，并用可执行用例守住 24 条禁用别名。
- 加载/空/失败三态统一到一个组件；空态固定给「现状 + 原因 + 一个主按钮」，不再出现「暂无数据」的死胡同。

## 已知限制

- 编译落盘偶尔会把页面写进 `concepts/` 的子目录（如 `concepts/comparisons/`）。这些文件不属于页面口径、不计入页面总数，已单独排期修编译链路。

3. 术语看不懂 → 正文都是中文人话，技术原词收在 tooltip 和「高级」折叠区里。

# 七、技术债台账（原 07，T02802）

> 建单：T02802（前后端手工镜像类型通用契约守护）。本台账记录「已量化、已守护、仍有边界」的技术债，
> 供后续轮次直接接手，不靠 review 提醒。

## 1. 前后端手工镜像类型（T02773 → T02802）

### 缺陷形状

`api/src/types.ts` 与 `frontend/src/types.ts` 各写一份同名类型，两侧 tsconfig 的 `include` 都只有自己的
`src/**/*`。跨服务契约的字段名错配**编译器永远看不见**，测试原先也不覆盖，于是缺陷以「功能正常、显示被吃掉」
的形态长期潜伏（真实案例：后端 `totalFreedMb` / 前端读 `total_freed_mb`，「释放 X MB」永不显示——T02773）。

### 清点口径（为什么这次可信）

用 TypeScript Compiler API 解析两份源码的 AST，而不是正则：

- 字段名取自属性/方法签名，`extends` 链与交叉类型成员一并内联展开，索引签名记作 `[index]`；
- 字符串字面量联合（`KnowledgeStatus`、`RefAuthority`）另按**成员集合**比对，不看字段名；
- 类型引用可解析到本文件内的声明则展开，外部/内置类型进 `notes` 交人工复核。

⚠ 反面教材：T02773 排查时那段临时正则把 `CleanupStorageStatus` 误判成「后端缺 `runState`/`runLogs`」
（实际就在 `api/src/types.ts`，是解析器被嵌套对象带偏），当时报出的「4 个类型漂移」只能当线索。
本轮 AST 复核结论：**两侧同名类型 27 个，字段集合有差异的 3 个**（`CleanupStorageStatus` 一致）。
该误判已写成回归锁用例（`api/test/mirror-types-contract.test.ts` 的「AST 口径复核 T02773 踩过的正则坑」）。

### 三处差异的判定与处置

| 类型 | 差异 | 判定 | 处置 |
| --- | --- | --- | --- |
| `BatchFixRequest` | 前端有 `issueKeys?`，后端镜像没有 | 错配（契约键只写在一侧） | **已修**：`api/src/types.ts` 补 `issueKeys?: string[]`，`api/src/routes/health-check.ts` 去掉就地 `& { issueKeys?: string[] }` 补丁 |
| `McpServerEntry` | 后端有 `triggerKeywords?`、`placeholderTools?`，前端镜像没有 | 错配 + **真实丢数据路径** | **已修**：前端镜像补两键；JSON 编辑模式的 stdio 重建改为按 `name` 带回 `timeoutMs`/`triggerKeywords`/`placeholderTools`（逻辑抽到 `frontend/src/utils/mcpConfigMode.ts`，配套 7 例单测） |
| `MultimodalOutput` | 前端多 `pptxUrl?` | 有意裁剪（前端是卡片渲染超集） | **登记不改**：`pptxUrl` 由前端把 `ppt` 事件的下载地址映射进卡片形状（`frontend/src/views/Query.vue`），后端 multimodal 事件不发这个键，卡片用 `v-if` 隐藏下载按钮，不是吃掉显示 |

其余 24 个同名类型判定为 `aligned`；另登记一对**跨名镜像**（后端 `FixInput` ↔ 前端 `FixRequest`，
批量修复请求体的 `items` 元素）——同名比对抓不到它，故显式配对锁住。

### 现在的守护

- 数据：`docs/mirror-types.json`（每个同名类型一条，判定 + 差异集合 + 必填理由；跨名对放 `pairs`）；
- 用例：`api/test/mirror-types-contract.test.ts`（7 例，放在 api 侧是因为它同时读两份源码，任一侧改名都会红）：
  登记表与代码一一对应（新增同名未登记即红、登记失效也红）、逐条按判定比对字段集合、
  字面量联合成员比对、条目自审（verdict 合法 / 理由必填 / 差异集合只在非对齐时出现）、
  AST 解析下限与空跑守卫、合成形状反向用例。
- 变异验证：8 个探针 8/8 关掉即红（改名、删字段、新增未登记、把裁剪清单写错、给字面量联合加一档、
  理由清空、登记表漏一条、合并逻辑不再带回懒加载键），每个探针后源文件逐字节还原并复核一致。

### 已知边界（下一轮要不要收，按单判定）

1. **只覆盖两份 `types.ts`**。两侧其他文件里导出的类型（如 `api/src/types.ts` 之外散落的请求/响应形状、
   `frontend/src/types/media.ts`）不在守护面内。同名比对天然抓不到「两侧起名不同」的镜像对，
   跨名对目前只有 `FixInput/FixRequest` 一条，是人工发现的——守护只保证登记后不再漂移。
2. `wiki-harness` 包与 api 之间的类型契约同样没有跨包锁（该包有自己的 tsconfig，两侧不互引）。
3. 登记表的判定是**人工裁决的记录**，守护只锁住「实际形状 = 登记的形状」，不会替你判断新差异该算缺陷还是裁剪。

## 2. MCP 配置 JSON 模式往返（本轮发现，未修）

`frontend/src/views/Config.vue` 的 JSON 编辑模式与表单模式双向切换时：

- `serializeMcpToJson` 只写出 `transport === 'stdio' && enabled` 的条目（注释写明是为了兼容 Claude Desktop 格式）；
- 回到表单时，stdio 条目**以 JSON 为权威源重建**，JSON 里没有的同名 stdio 视为已删除。

合起来的效果：**一个 `enabled: false` 的 stdio MCP server，在「切到 JSON 模式再切回来」这一步就被静默删掉**，
而保存是整份配置回传。这与上面 T02773/T02802 的「显示被吃掉」不同层级——它是配置数据丢失。
是否要改成「保留禁用态条目」或「在 JSON 里写非标准键」属于产品口径取舍，已建单待裁决，见 T02834。
