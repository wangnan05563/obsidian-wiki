## 1. 评审结论概览

| 维度 | 评分 | 说明 |
| --- | --- | --- |
| 文档结构完整性 | ✅ 优 | 11 章 + 3 附录齐全，竞品调研详实，趋势分析到位 |
| 与 V2.2 基线一致性 | ❌ 差 | 4 项需求与 V2.2 §2.3 "不含"约束冲突，需重新界定范围 |

**总体结论**：V3.0 SRS 作为"竞品调研与功能候选清单"**有价值**，但作为"立即可执行的需求规格"**不可用**。须修订 4 项 P0 阻塞问题 + 6 项过度设计后，方可作为下一迭代基准。

**核心建议**：将 V3.0 降级为"V3.0 候选功能池（Candidate Pool）"，**先解决 v0.1.0 的 3 项 P0 阻塞问题，再从候选池中精选 3-5 项作为 v0.2 增量**，而非一次性吞下 30+ 功能点。

## 2. P0 阻塞问题（必须修正后才能作为实施基准）

### P0-1：与 V2.2 §2.3 "不含"约束的 4 项冲突

**位置**：V3.0 FR-13 / FR-15 / FR-16 vs V2.2 §2.3

**问题描述**：

V2.2 §2.3 明确"不含（二期）"：
- 团队级权限管理、SSO
- 移动端原生 App（依赖 TRAE Work 移动端或 PWA）
- **不自建向量库，不实现 RAG 检索（明确采用 LLM Wiki 路线而非 RAG）**

V3.0 新增需求与上述约束直接冲突：

| V3.0 需求 | 冲突约束 | 冲突原因 |
| --- | --- | --- |
| FR-13-3 音频/视频转写入库 | 移动端原生 App | 引入新外部依赖（Whisper API） |
| FR-15-6 NLP 抽取实体建立关系图谱 | 不自建向量库 / 不实现 RAG | NLP 抽取需引入 NER 模型，与 LLM Wiki 纯编译路线冲突 |
| FR-16-2 联邦搜索（接入 GitHub/书签/外部源） | 单用户本地使用 | 跨源检索实质是联邦 RAG，与 V2.2 "明确采用 LLM Wiki 路线而非 RAG" 直接冲突 |
| FR-13-1 PDF 智能对话 | 不自建向量库 | "PDF 对话"语义模糊——是编译入库后对话（合规）还是 PDF 即时 RAG（违规）？ |

**修复建议**：

1. **FR-13-1 PDF 智能对话**明确为"PDF 解析入库为 Markdown → 走 compile 工作流 → 基于已编译页面问答"，**不得**走"PDF 即时分块 + 向量检索 + LLM 问答"的 RAG 路径。
2. **FR-15-6 NLP 抽取实体**改为"由 LLM 在 compile 阶段抽取实体并写入 frontmatter `entities` 字段"，**不得**引入独立 NER 模型或向量库。
3. **FR-16-2 联邦搜索**降级为 P3 长期方向，且明确"外部源须先 ingest 到 raw/ 走 compile 工作流，不得跨源 RAG"。
4. **FR-13-3 音视频转写**降级为 P3，且明确"转写为 Markdown 后入库，不做音视频直接 RAG"。

### P0-2：与未解决的 3 项 P0 阻塞问题优先级倒置

**位置**：V3.0 §6.1 P0 立即可做 vs 知识库问答 AI 对话流 SRS 评审报告 §2.1

**问题描述**：

项目当前存在 3 项 P0 阻塞问题（2026-07-11 评审报告提出，至今未解决）：

| 现有 P0 阻塞 | 状态 | 影响 |
| --- | --- | --- |

| ChatMessage 数据模型 breaking change 无迁移策略 | 未解决 | v1 → v2 数据迁移断裂 |
| 与核心架构脱节（降级链 + per-session Lock + EngineAdapter 未提及） | 未解决 | v2 新增 thinking/多模态事件无法挂载 |

V3.0 在此背景下新增 4 项 P0 演进需求（RefsList 强化 / AI 标签 / Discover Sources / Query 输出模式），**与现有 P0 阻塞形成优先级倒置**：

- V3.0 P0-1 强化 RefsList：依赖 v2 对话流的 Reference[] 结构（P0-2 未解决）

- V3.0 P0-4 Query 输出模式：依赖对话流降级链（P0-3 未解决）

**修复建议**：

1. V3.0 §6.1 P0 项全部降级为"前置 P0 解决后的 P1"。
2. 新增 §6.0 "P0 阻塞清空"章节，明确 V3.0 演进启动前须先解决现有 3 项 P0 阻塞问题。
3. V3.0 路线图阶段 3a 改为"v0.2 阻塞清空 + 对话流 v2 落地"，阶段 3b 起再启动 V3.0 演进。

### P0-3：FR-12 Skill Adapter 与 V2.2 EngineAdapter 关系模糊

**位置**：V3.0 §7.4 FR-12 vs V2.2 §5.5 FR-05 / V1.3 概要设计 §6.3

**问题描述**：

V2.2 已有 EngineAdapter 接口（compile/resumeCompile/query/healthCheck/healthCheckFix）+ HarnessAdapter 实现 + `updateConfig({ model, budget, staleDays })` 即时生效。

V3.0 FR-12 提出"扩展 EngineAdapter 为 Skill Adapter（模型+范围+系统提示词+工具集）"，但：

1. **"扩展"还是"替换"？** 未明确——是 EngineAdapter 接口增加方法，还是新增 SkillAdapter 接口并行？
2. **与现有 `updateConfig` 的关系？** 现有 `updateConfig({ model })` 已能切换模型，Skill Adapter 的"模型+范围+系统提示词+工具集"是否退化为 `updateConfig({ model, scope, systemPrompt, tools })`？
3. **AC-12-5 引用范围严格执行**：现有 query 工作流是基于 `index.md` + 全库搜索的，如何实现"范围限定为 `folder: concepts/` 时不得检索其他目录"？这需要重构 query 工作流的检索逻辑，与 V2.2 §9.2 问答工作流（WF-02）冲突。

**修复建议**：

1. FR-12 明确为"EngineAdapter 接口扩展 `updateConfig` 参数 + 新增 `getSkillConfig()` 方法"，**不新增 SkillAdapter 接口**。
2. AC-12-5 引用范围限定改为"在 query 工作流的 search 工具中传入 `scopeFilter` 参数"，**不重构 query 工作流**。
3. AC-12-3 "Skill 定义为 Markdown 文件"改为"Skill 配置存入 config.json 的 `skills` 数组"，避免引入新的文件类型与解析逻辑。

### P0-4：FR-14 YAML DSL 与现有 TS 工作流的关系是工程债而非用户价值

**位置**：V3.0 §7.6 FR-14 vs 现有 `workflows/*.ts`

**问题描述**：

V3.0 FR-14 提出"将 compile/query/health-check workflow 从 TS 硬编码改为 YAML 声明式"，借鉴 Dify。

但项目现状：
- 3 个 workflow TS 实现已稳定（DELIVERY.md 已交付并通过验证）
- workflow 核心是 `harness.run({ task, tools, hooks })` 调用，TS 内联即可表达
- Dify 的 YAML DSL 服务于"非开发者可视化搭建 LLM 应用"场景，本项目是"自研专用引擎"，**用户不直接编辑 workflow**

**这是工程债驱动而非用户价值驱动**：
- 用户价值：用户不会因"workflow 是 YAML 还是 TS"而感知差异
- 工程债：开发者可能觉得 TS 硬编码难维护，但这应通过代码重构解决，而非引入 YAML DSL 抽象层

**修复建议**：

1. FR-14-1 YAML DSL **删除**或降级为 P3 长期方向。
2. FR-14-2 Prompt IDE 保留为 P1（用户价值明确——独立调试 prompt）。
3. FR-14-3 Logs + Monitor 保留为 P2（与 DELIVERY.md §4.2 §12.3-8 已交付的 run-logger.ts 整合，不重复造轮子）。

### P1-5：FR-16 Discover Sources 与现有 Graph.vue 信息架构冲突

**位置**：V3.0 §7.8 FR-16-1 vs DELIVERY.md §3.4 Graph.vue

**问题描述**：

V3.0 AC-16-1 说"Graph.vue 节点点击时在侧边栏推荐 ≥ 3 个相关笔记"。

但现有 Graph.vue 已有 §12.3-2 大节点降级机制（200/500 节点三级阈值），节点点击行为当前是"跳转到对应笔记"。新增"侧边栏推荐"会：

1. **改变现有交互模式**：节点点击从"跳转"变为"展开侧边栏"，破坏现有用户体验。
2. **"邻近但未连接"的语义模糊**：是基于双链拓扑距离？还是语义相似度？后者需要向量库（P0-1 冲突）。
3. **"一键建立双链"机制**：自动插入 `[[页面名]]` 可能污染用户笔记内容，须明确插入位置（frontmatter `related` 字段？还是正文末尾？）。

**修复建议**：

1. AC-16-1 改为"节点**右键**时在侧边栏推荐"（不破坏现有左键跳转）。
2. AC-16-2 推荐理由仅基于"双链拓扑"（同标签/同作者/同目录），**不引入语义相似度**。
3. AC-16-3 "一键建立双链"明确为"在两篇笔记的 frontmatter 新增 `related: [[页面名]]` 字段"，**不修改正文**。

### P1-6：NFR-07 多模态性能指标与现有 NFR-01 重复

**位置**：V3.0 §8.1 NFR-07 vs V2.2 §6.1 NFR-01

**问题描述**：

1. NFR-07 删除"流式首字 ≤ 3 秒"（与 NFR-01 重复）。
2. "PDF 解析 ≤ 30 秒"明确为"PDF 解析为 Markdown 文本耗时 ≤ 30 秒，不含后续 compile"。
3. 其余指标保留，但标注"含模型推理时间"或"不含模型推理时间"以避免歧义。

## 7. 路线漂移风险深度分析

V3.0 §10.3 声明"不退化 compile 为查询时 RAG"，但实际有 3 处隐性漂移：

### 7.1 FR-13-1 "PDF 智能对话"语义模糊

"PDF 智能对话"在 WPS AI 语境下是"PDF 即时分块 + 向量检索 + LLM 问答"（典型 RAG）。

V3.0 未明确区分：
- **合规路径**：PDF 解析为 Markdown → 入 raw/ → compile 工作流编译为结构化页面 → 基于已编译页面问答（LLM Wiki 路线）
- **违规路径**：PDF 即时分块 → 向量检索 → LLM 问答（RAG 路线）

**修复**：FR-13-1 重命名为"PDF 解析入库"，明确走 compile 工作流，删除"智能对话"表述。

### 7.2 FR-16-2 联邦搜索本质是跨源 RAG

"联邦搜索"在 Notion Connectors 语境下是"跨外部数据源统一问答"——需要将外部源分块向量化后统一检索，本质是跨源 RAG。

V3.0 §10.3 声明"不借鉴 RAG 替代编译"，但 FR-16-2 联邦搜索实质引入了 RAG。

**修复**：FR-16-2 改为"外部源 Connector 仅用于 ingest 到 raw/，不参与运行时问答"，即外部源须先 compile 入库，再走 LLM Wiki 问答。

### 7.3 FR-15-6 NLP 抽取引入独立 NER 模型

"NLP 抽取实体建立关系图谱"在 MS Graph 语境下是独立 NER 模型 + 知识图谱数据库。

V3.0 §10.3 声明"不放弃双向链接图谱"，但 FR-15-6 引入 NER 模型与 V2.2 "不建向量库"约束冲突。

**修复**：FR-15-6 改为"由 LLM 在 compile 阶段抽取实体并写入 frontmatter `entities` 字段 + `[[双向链接]]`"，不引入独立 NER 模型。
